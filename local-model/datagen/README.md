# Генератор обучающих данных

Реальных размеченных диалогов у нас было очень мало (около 40), а для обучения нейросети нужны тысячи. Поэтому мы
написали генератор: он собирает синтетические диалоги клиента с оператором из шаблонов и сразу знает правильные
ответы по чек-листу. Плюс он делает изменённые копии реальных диалогов из DEV, например вставляет туда чих
оператора или грубость.

## Как запустить

Проще всего из корня проекта:
```
npm run datagen
```
Это займёт около минуты. Скрипт сам найдёт Python (`py -3`, `python` или `python3`), сгенерирует 8000 диалогов,
сделает копии реальных диалогов, проверит разметку и подготовит события для обучения.

Можно и по шагам, из папки `local-model/datagen` (на Windows вместо `python` можно писать `py -3`):
```
python generate.py --n 8000 --seed 7 --out ../data
python augment_dev.py --copies 6 --out ../data
python check.py --data ../data
```
Нужен только Python 3.10+, сторонние библиотеки не требуются. Меньше диалогов для быстрой проверки:
`npm run datagen -- --n 2000`. Только проверка уже готовых данных: `npm run datagen:check`.

## Что получается в `local-model/data/`

| Файл | Что внутри |
|---|---|
| `synth_dialogs.json` | синтетические диалоги в том же формате, что отдаёт API организаторов |
| `synth_labels.jsonl` | правильные ответы по чек-листу, реплики-доказательства, сценарий диалога |
| `aug_dev_dialogs.json`, `aug_dev_labels.jsonl` | копии реальных диалогов DEV со вставками (чих, эмодзи, капс, грубость и т. д.) |
| `question_bank.json` | все вопросы: критерии стартового чек-листа, их перефразировки и «новые» критерии |
| `pairs_train.jsonl`, `pairs_val.jsonl`, `pairs_test.jsonl` | готовые пары «диалог + вопрос → ответ» для обучения, валидации и теста |
| `pairs_zero_shot.jsonl` | пары по критериям, которых нет в обучении, — чтобы проверить, справится ли модель с новым |
| `SYNTH.json`, `gt-synth/` | 150 диалогов, чтобы посмотреть синтетику в интерфейсе и сравнить модель с разметкой |
| `stats.json` | статистика: сколько диалогов по языкам, темам, ответам |

Большие файлы в репозиторий не кладём, они пересоздаются командой `npm run datagen`.

## Что есть в синтетике

- **18 тем** из работы брокера: тарифы, вывод и пополнение денег, отклонённые заявки, вход в приложение, документы,
  налоговые справки, дивиденды, комиссии, обмен валют, сбои приложения и другие. Для каждой темы есть ответы
  разного качества: полный, неполный, размытый и ошибочный.
- **Три языка:** русский (50%), казахский (25%) и английский (25%). Есть чаты и звонки. У звонков, как в реальных
  данных, скрытые персональные данные (`[Имя скрыто]`), время в формате ISO и «шум» распознавания речи.
- **Разное поведение оператора** по каждому критерию, включая редкие случаи: поздоровался не на том языке,
  переспросил то, что клиент уже сказал, раскрыл данные до проверки личности, ушёл ждать без предупреждения,
  ответил не на тот вопрос, молча закрыл чат, связь оборвалась, грубые нарушения.
- **16 «необычных» поведений оператора:** чих, кашель, эмодзи, сленг, обращение на «ты», капс, опечатки, ссылка на
  конкурентов, обещание перезвонить, еда на рабочем месте и т. д. Это нужно, чтобы модель могла справиться с
  критериями, которые организаторы могут добавить на защите.
- **Отвлекающее поведение клиента:** клиент тоже может чихнуть или писать капсом. Так модель учится, что оценивается
  только оператор.

## Формат разметки

Строка из `synth_labels.jsonl`:
```json
{"conversation_id": "syn-ru-c-00000",
 "answers":  {"c01": "yes", "c02": "yes", "c03": "no", "c04": 20, "c05": "yes", "c06": 10, "c07": "no", "c08": "no"},
 "evidence": {"c03": [12, 13, 15], "c07": [19]},
 "ambiguous": ["c05"],
 "split": "train"}
```
- `answers` — ответы по критериям, в том же формате, что и ручная разметка в `data/gt/`.
- `evidence` — номера реплик, которые доказывают ответ.
- `ambiguous` — критерии, где даже два человека могли бы ответить по-разному. Их лучше не учитывать в метриках.

Строка из `pairs_*.jsonl`:
```json
{"d": "syn-ru-c-00000", "q": "n_op_sneezed", "w": 1, "y": "no", "ev": []}
```
Здесь `d` — id диалога, `q` — id вопроса из `question_bank.json`, `w` — номер формулировки вопроса, `y` — правильный
ответ, `ev` — номера реплик-доказательств. Вопрос хранится в том же виде, что и критерий в редакторе чек-листа
(название, описание, тип, ступени шкалы, разрешён ли N/A), то есть модель при обучении видит ровно то же, что
потом получит из интерфейса.

## Разбиение на train / val / test

- Каждый диалог целиком попадает в одну часть: 80% train, 10% val, 10% test. Один и тот же диалог не может
  оказаться и в обучении, и в тесте.
- Вопросы про кашель, еду на рабочем месте и конкурентов в обучение не попадают специально: на них мы проверяем,
  как модель справляется с совсем новыми критериями.
- Копии диалогов из `data/gt-holdout` всегда идут в test. На них обучаться нельзя, иначе проверка будет нечестной.

## Проверка через приложение

Выборку `data/SYNTH.json` можно открыть в интерфейсе как обычный набор (group_id `SYNTH`). Оценить её моделью и
сравнить с разметкой генератора:
```
npm run eval -- --group SYNTH
npm run accuracy -- --gt local-model/data/gt-synth --verbose 1
```

## Как добавить что-то своё

- Новая тема — словарь в `topics.py` (на трёх языках, с ответами разного качества).
- Новое поведение оператора — фразы в `banks.py` и вопрос в `questions.py`. Если оно влияет на стартовые
  критерии, это прописывается в `labels.py`.
- Если поменялся стартовый чек-лист, править нужно только `labels.py`.

## Ограничения

- Казахские тексты мы писали сами, носитель языка их не проверял.
- Синтетика однообразна по структуре: почти всегда сначала бот, потом передача оператору, потом оператор, как в DEV.
- «Корректность консультации» размечена по тому, какой ответ выбрал генератор (полный, неполный и т. д.), а не по
  смыслу. Поэтому модель умеет это различать только в пределах наших 18 тем.
